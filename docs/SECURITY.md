# Security Baseline — Health Memory Agent

**Version:** 0.1 (Phase 0)  
**Status:** Baseline established — not production-ready  
**Last Updated:** Phase 0

> **Important:** This document describes the security baseline for development and the requirements for production-grade security. Health Memory Agent handles sensitive personal health information. All future phases must consider the security requirements documented here.

---

## 1. Current Baseline (Phase 0)

### Secrets Management
- ✅ `.gitignore` excludes all `.env` files, preventing accidental secret commits
- ✅ `.env.example` templates document required variables without real values
- ✅ Service-role credentials are backend-only — never sent to the browser
- ✅ No credentials are hardcoded in source files
- ✅ Environment variables are validated at startup — missing required vars cause a clear error

### API Security
- ✅ Centralized error handling prevents stack traces from reaching clients in production
- ✅ Request logging does not log request bodies (which may contain sensitive data)
- 🔜 HTTP security headers (helmet) — to be configured when authentication is added
- 🔜 CORS configuration — to be locked down in Phase 1 with known frontend origin
- 🔜 Rate limiting — to be added in Phase 1

### Database Security
- ✅ Database access is server-side only in Phase 0
- 🔜 RLS policies — required on every table before Phase 1 goes live
- 🔜 Parameterized queries — enforced by Supabase JS client (no raw SQL string interpolation)

## 2. Supabase Key Handling

| Key Type | Where Used | Where NOT Used |
|----------|-----------|----------------|
| `anon` / public key | Frontend browser (future: auth, realtime) | Backend privileged operations |
| `service_role` key | Backend server ONLY (repositories) | Frontend, browser, logs, responses |

**The service-role key bypasses all RLS policies.** It must never be exposed to the browser. If it is ever committed to Git or exposed in a log, treat it as compromised and rotate it immediately via the Supabase dashboard.

---

## 3. Authentication Security (Phase 1 Requirements)

When implementing authentication in Phase 1:

- Use Supabase Auth — do not build a custom authentication system
- Evaluate **httpOnly cookie** storage for refresh tokens (recommended — prevents XSS token theft)
- Access tokens should be short-lived (Supabase default: 1 hour)
- Implement CSRF protection if cookie-based auth is used
- Logout must invalidate the session server-side, not just clear client storage
- Password reset flows must use time-limited, single-use tokens
- Log authentication events (login, logout, failed attempts) — but never log passwords or tokens

---

## 4. Medical Record Privacy (Phase 2 Requirements)

Health Memory Agent stores personal health information (PHI). When Phase 2 is implemented:

- All medical documents must be stored in **private** Supabase Storage buckets
- Files must not be accessible via direct public URLs
- Access must be granted through **signed URLs** with expiry times, generated by the backend after authorization checks
- Document metadata in the database must be protected by RLS
- Consider encrypting particularly sensitive fields at the application layer (Phase 9)
- Audit logging for document access should be implemented (who accessed what, when)
- Data retention policies should be defined and implemented

---

## 5. API Input Validation (All Phases)

- All API endpoints must validate input using Zod schemas in `validators/`
- Validation happens in middleware before reaching controllers
- Reject unexpected fields (use strict schemas)
- Validate file types and sizes before storing
- Sanitize text inputs to prevent injection attacks (Supabase JS client uses parameterized queries — do not bypass this)

---

## 6. Logging Security

**Never log:**
- Passwords or password hashes
- API keys or tokens (full or partial)
- Supabase keys
- Full credit card numbers
- Social security numbers or national ID numbers
- Full medical record content
- User email addresses in non-auth log contexts

**Safe to log:**
- Request method, path, and status code
- User ID (UUID) — not email or name
- Timestamps
- Error types (without stack traces in production)
- Performance metrics

---

## 7. HTTP Security Headers (Phase 1+)

Configure with `helmet` middleware:

| Header | Recommended Setting |
|--------|-------------------|
| `Content-Security-Policy` | Restrict to known origins |
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | Restrict camera/mic/location to needed features |

---

## 8. CORS Policy (Phase 1+)

In production:
- Allow only the known frontend domain
- Do not use `origin: '*'` in production
- Credentials mode must be set correctly for cookie-based auth

In development:
- Allow `localhost:5173` (Vite dev server) only

## 9. SOS and Emergency Feature Security (Phase 5–6)

When implementing SOS functionality:

- SOS demo mode must be clearly labeled as simulated — no real calls or messages in demo mode
- Live test mode (Phase 6) must require explicit consent from all recipients
- Recipient phone numbers and contact details must be encrypted at rest
- SOS event logs must be retained for audit purposes but protected by RLS
- Rate limiting must prevent SOS abuse

---

## 10. Compliance Considerations (Phase 9)

Before any production deployment handling real patient data:

- Evaluate HIPAA compliance requirements (if US-based)
- Evaluate applicable local healthcare data privacy laws
- Implement formal audit logging
- Define and document data retention and deletion policies
- Implement right-to-erasure (data deletion) workflows
- Consider a formal security audit

---

## 11. Incident Response

If a security issue is discovered:
1. Immediately rotate any potentially compromised credentials
2. Document the issue in a private, non-public channel
3. Assess scope of potential data exposure
4. Notify affected users if required by applicable law
5. Remediate and document in a post-incident review

## 13. Phase 5 Emergency SOS Demo Mode Safety Boundary

Phase 5 operates strictly within a sandboxed **Demo Simulation Boundary**:

1. **Zero External Communications:**
   - No SMS, Twilio, Plivo, AWS SNS, Telnyx, or voice providers can be invoked.
   - No real hospital endpoints or ambulance dispatch APIs are connected.
   - Calling or dispatching to emergency services (e.g. India 112) is strictly forbidden and structurally impossible in code.
2. **Explicit Simulation Provenance:**
   - Every incident, contact attempt, audit event, and hospital handoff record is stamped with `is_demo: true` and `simulation_provenance: 'DEMO_SIMULATION_ONLY'`.
   - Seeded emergency contact phone numbers use clearly non-dialable formats (e.g. `+91-98765-00001 (Simulated)`).
   - Fictional receiving hospital identities are prominently marked as simulated (e.g. `Apollo Indraprastha Fictional Hospital (Demo Desk)`).
3. **Cross-Family and Patient Authorization Isolation:**
   - All emergency incident and handoff queries enforce server-side family membership verification (`requireFamilyRole`).
   - A user from Family B cannot trigger, inspect, acknowledge, or cancel incidents belonging to Family A.
4. **Safe Scenario Reset:**
   - The demo reset endpoint (`POST /api/families/:familyId/sos/demo/reset`) operates strictly within the target patient profile and family workspace. It cleans up only demo incidents, attempts, events, and handoffs without altering or deleting other family workspaces, patient records, or real accounts.

## 14. Phase 6 Controlled Live Test Mode Security & Guardrails

Phase 6 introduces real outbound carrier integrations with strict multi-layer defense-in-depth safety guardrails:

1. **Zero Real Emergency Services or Hospital Contacts:**
   - Dialing or messaging emergency numbers (`112`, `911`, `100`, `101`, `102`, `108`, `1091`, `1098`) is structurally intercepted and rejected server-side with HTTP 400.
   - Caregiver escalation and hospital handoffs remain 100% simulated.
2. **Rejection of Seeded Demo Contacts:**
   - Seeded demo contacts (e.g. `+91-98765-XXXXX (Simulated)`) and arbitrary unverified phone numbers are strictly prohibited from receiving outbound communications.
3. **Mandatory Explicit Consent & Onboarding:**
   - Only consenting team members registered in `live_test_recipients` can receive test communications.
   - Consent status (`CONSENT_GRANTED` vs `CONSENT_REVOKED`) is checked at execution time.
   - Revoking consent immediately invalidates all future dispatches without delay.
4. **Per-Test Preflight Operator Confirmation:**
   - No automatic live dispatches occur on boot, seeding, test execution, or normal SOS clicks.
   - Every single live dispatch requires manual review of masked destination details, exact outgoing message preview, and an explicit operator confirmation checkbox.
5. **Zero Clinical PHI over Unencrypted Telecom Channels:**
   - Outgoing SMS and automated voice scripts contain only safe, synthetic demonstration notices and incident numbers. No medical records, lab reports, or sensitive health data are ever transmitted.
6. **Cryptographic Webhook Signature Verification & Idempotency:**
   - Provider delivery callbacks (`/api/telephony/callbacks/:provider`) verify cryptographic signatures (e.g., Twilio HMAC-SHA1 `X-Twilio-Signature`).
   - Webhook callback processing enforces strict in-memory and database idempotency, preventing replay attacks or duplicate transitions.
7. **Rate Limiting & Safety Caps:**
   - A server-side safety cap enforces a maximum of 3 recipients per test run.
   - A configurable cooldown timer prevents rapid sequential dispatches per family workspace.
8. **Credential Protection:**
   - Twilio Account SID/Auth Token and Exotel API credentials reside solely in server environment variables and are never transmitted to the browser or ordinary application logs.

## 15. Phase 7 Offline-First Data Protection & Local Storage Security

Phase 7 introduces local browser persistence for offline capabilities with strict security controls:

1. **Zero Clinical Data in Public Service Worker Cache:**
   - The Service Worker (`sw.js`) explicitly excludes all `/api/*` paths from `CacheStorage`.
   - Private patient profiles, medical documents, lab results, and auth tokens are NEVER cached in public browser HTTP caches.
2. **Account-Aware Storage Partitioning:**
   - All IndexedDB keys in `sanjivani_offline_db` are prefixed by `userId`.
   - On shared family tablets or multi-user workstations, one authenticated user cannot access or query another user's cached snapshots.
3. **Automatic Cleanup on Signout:**
   - Invoking `logout()` triggers immediate execution of `offlineStorage.clearUserData(user.id)`, wiping local patient snapshots, downloaded records, and sync queues for that user.
4. **Server-Side Authorization on Every Queued Write:**
   - The authoritative server does not trust client-claimed permissions.
   - When synchronizing queued operations, the server re-validates the user's family membership and patient profile ownership at submission time.
   - Revoked caregiver access results in immediate HTTP 403 rejection.
5. **Idempotency & Duplicate Protection:**
   - Every offline-queued write contains a client-generated UUID and idempotency key.
   - Server-side unique constraints prevent duplicate records, duplicated doses, or double-booked appointments upon network retries.
6. **No Silent Re-creation of Cancelled Records:**
   - Offline updates attempting to modify or revive appointments cancelled on the server are structurally rejected with conflict warnings.
7. **Offline Emergency Safeguards:**
   - The application explicitly warns users when offline that real emergency services (112) cannot be contacted via the offline browser and directs them to dial directly.

## 16. Phase 8 Health Community & Society Network Security & Privacy Safeguards

Phase 8 introduces a hyperlocal community mutual assistance and blood-donor coordination network with strict medical privacy isolation and anti-abuse safeguards:

1. **Complete Healthcare Privacy Isolation:**
   - Community tables (`community_groups`, `community_memberships`, `assistance_requests`, `blood_donor_requests`) have **zero links or foreign keys** to private family workspaces or patient medical records (`patient_profiles`, `medical_documents`, `extracted_fields`, `ai_health_memories`).
   - Community owners and moderators have **zero authority** over family workspaces. Route authorization strictly checks family memberships, returning `403 Forbidden` if a community manager attempts to inspect member medical documents or patient profiles.
2. **Privacy-First Contact Sharing & Time-Bound Grants:**
   - By default, assistance requests display only an approximate locality (e.g. "Tower B, 4th Floor"). Exact addresses and phone numbers are scrubbed from general community responses.
   - Contact details are shared **only** upon explicit creator assignment or contact confirmation through `contact_sharing_grants`.
   - Contact grants are strictly time-bound (e.g., 72 hours) and can be immediately revoked by the requester at any time.
3. **Non-Emergency Boundary Enforcement:**
   - Creating an assistance request requires explicit confirmation that the request is for non-emergency neighborly help.
   - Prominent disclaimer banners warn users that community assistance is **NOT** an emergency dispatch service and directs acute trauma/cardiac cases to 112 / Ambulance services.
4. **Blood Donation Clinical Disclaimers:**
   - Sanjivani coordinates voluntary contact between donors and patient families. It explicitly disclaims any biological testing, infectious disease screening (HIV, Hepatitis, Syphilis, Malaria), or antibody cross-matching.
   - All clinical screening and collection remain exclusively under the legal and medical responsibility of licensed blood banks and hospital pathology departments.
5. **Anti-Abuse & Moderation Audit Trail:**
   - Members can report spam, harassment, inappropriate clinical advice, or commercial solicitation.
   - Owners and moderators review flagged content and can take structured actions (`warn_user`, `hide_content`, `suspend_member`, `remove_member`, `dismiss`).
   - All moderation decisions generate immutable audit records in `moderation_actions` with moderator IDs, timestamps, and justification notes.
6. **Secure Membership & Invitation Lifecycle:**
   - Community invitations use cryptographically random alphanumeric codes with expiration timestamps (7-day TTL).
   - Upon acceptance, invitation status transitions to `accepted` and cannot be re-used by third parties.
   - Join requests for `approval_required` groups require moderator approval before membership activation.
